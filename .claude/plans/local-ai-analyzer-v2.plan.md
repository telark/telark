## Approach

Keep the service, the stream worker, the four read-only tools, the insight lifecycle (dedup id, merge, resolve, prune), the SSE fan-out, the Settings section and the chart slot exactly as they are. Replace *what a run does* with a two-stage pipeline: **(1) gather + rules** — the worker calls the existing tool handlers directly (overview, change history, ≤3 workload statuses, warning events; ≤ 1 s, ≤ 4 + 3 GETs), and a pure `rules.py` turns those payloads into candidate insights (kind, subject, severity, confidence, evidence refs, template title/summary) — deterministic, testable, ms; the document is written and announced at this point, so the UI shows the cards ~1–2 s after Analyze; **(2) narration** — ONE `/api/chat` call, no tools array, `format` = a tiny JSON schema (`title` ≤ 80, `summary` ≤ 240 chars per insight, `minItems = maxItems = n`), `think:false`, `num_predict = 16 + 120·n`, `options.num_thread` = pod CPU, `num_ctx 4096`, `keep_alive -1`, 45 s timeout, one attempt; on success only `title`/`summary` of the just-written cards are replaced (`insight.updated`), on any failure the template prose stays and the run is still `done` (steps = 0 means "rules only"). The current multi-step tool loop is kept verbatim as **deep mode** (`ANALYZER_MODE=deep`, a chart value for ≥ 4 vCPU or GPU); fast is the default. Two runtime defects are fixed in the chart + client: thread oversubscription (`num_thread` on every request, `ollama.resources.limits.cpu: "2"`) and the page-cache memory refusal (`limits.memory` removed, `keep_alive -1`). Modes are a deploy-time contract in chart values: `app.ollama.autoPull=true` = connected (443 egress for pulls), `false` = air-gapped (no egress, pre-seeded model); `app.ollama.runtimeUrl` points the analyzer at a customer-run OSS Ollama-API endpoint (URL only, no key). No CRD schema, exporter, discovery or persisted-document change; the UI change is a model catalog, two hints and a run line.

## Decisions (defaults; the user answers only to disagree)

- **D1 — Rules first, model narrates (research Q1).** Yes. Insights exist with no model at all (steps = 0); the narration only rewrites `title`/`summary`. The design's "model proposes, code checks" sentence becomes "code decides, model phrases"; in deep mode the emitted kinds/refs still pass `insights.validate` as today. *Why:* the eight insight kinds are exactly what k8sgpt-style rules detect from data the tools already fetch; every vendor that runs on small CPU does this (k8sgpt, Davis); measured tool loops at ≤ 1.7B are 30–200 s per step and unreliable.
- **D2 — Default model `granite4:350m` (research Q2).** Seeds `DefaultAnalyzerModel`, the UI default and the Python `LICENSES`. `qwen3:1.7b` is the documented 4-vCPU / better-prose tier, `qwen3:4b` the GPU / deep tier. *Why:* the table above — the only Apache-2.0 model that narrates in ≈ 5 s and honours the schema on 2 vCPU; `qwen3:1.7b` narration is 14 s and its one-shot 70–110 s. `granite4:350m-h` (hybrid, less KV) is untested; V3 tries it once and the catalog gains it only if it is at least as fast and schema-valid.
- **D3 — No Ollama chart bump now (research Q3).** Stay on otwld 1.50.0 / Ollama 0.17.7. *Why:* the numbers above were taken on 0.17.7 and already show prefix reuse; the reported m7i `sapphirerapids` segfault (#17205) is a risk we cannot test in this plan; a bump is a one-line follow-up after V1–V5 pass (user-owned, listed below).
- **D4 — Remove `ollama.resources.limits.memory`, keep `requests.memory: 3Gi` (research Q4).** Ollama's free-memory check is `memory.max − memory.current`, and `memory.current` counts page cache (1.14 GB of file pages in the live pod right now), so *any* limit is eventually filled by pulled blobs and refused. With no limit `memory.max` is `max`, the parse falls back to `/proc/meminfo` MemAvailable, which is cache-aware. `keep_alive -1` additionally keeps the loaded model from being re-checked. *Trade:* Burstable QoS; the README documents the Guaranteed alternative (limit ≥ 3 × weights + 1 GiB, re-checked after every pull). V2 proves the refusal is gone.
- **D5 — Modes are chart-only; no CRD / Go / exporter / Settings field (research Q5).** `app.ollama.autoPull` is the switch it already is (true = connected, false = air-gapped: the NetworkPolicy drops 443 egress), documented under those names; new `app.ollama.runtimeUrl` (default `""`) replaces `OLLAMA_HOST` for a customer-run OSS endpoint that speaks the Ollama API (their own Ollama on a GPU host; no key, no Secret). The UI only *displays* the mode: `RuntimeStatus` gains `autoPull` and `mode` (fast|deep). *Why:* the CR cannot open egress, so a UI switch would be a lie; `ai.mode` in the CRD would need CRD → data → exporter → Settings for zero behaviour. OpenAI-compatible endpoints (llama-server, vLLM) are out of scope (research §5 `runtimeKind`, later).
- **D6 — Connected-mode egress stays port-443-only (research Q6).** FQDN allow-lists need Cilium/Calico; the README gets one sentence pointing at `CiliumNetworkPolicy toFQDNs registry.ollama.ai` for those clusters. Nothing templated.
- **D7 — Zero change to the persisted insight document and the SSE event names; one additive SSE payload change (`runtime.changed` + `mode`/`autoPull`, see Contract changes).** `LastRun.steps` = model calls that produced output (fast: 0 or 1; deep: as today), `LastRun.toolCalls` = gather/tool calls; the UI renders steps = 0 on a done run as "rules only". *Why:* `AppInsights` is decoded by discovery's read route into the Go struct (unknown fields would be dropped on re-encode), so any new document field means a data release + discovery pin bump for two cosmetic fields.
- **D8 — Narration scope.** One call per run, no tools, `title`/`summary` only, order-bound to the candidates (`minItems = maxItems = n`), one attempt, 45 s, `temperature 0.2`; empty strings keep the template; a wrong item count keeps all templates. Summary cap 240 chars (≈ 60 tokens) so three insights stay ≤ 25 s.
- **D9 — Fast mode needs an existing model, not the `tools` capability.** `runtime.check` reports `unsupported` only in deep mode; `validate` returns `model_lacks_tools` only in deep mode. The CRD `model` description loses "must expose the tools capability".
- **D10 — Catalog.** `granite4:350m` (default, CPU tiny), `qwen3:1.7b` (CPU 4 vCPU), `qwen3:4b` (GPU / deep), `qwen2.5:7b` (GPU) — all Apache-2.0. Dropped: `qwen2.5:3b` (Qwen Research licence), `qwen2.5:1.5b` (superseded), `qwen3.5:0.8b` (ignored the schema). The research-licence warning path stays in code (an operator can still type any tag).
- **D11 — Verification builds dev images.** `scripts/local-build-push.sh` builds Go services only (it exits on a service without `go.mod`, line 156), so V1 builds analyzer the NEXT_SESSION §3.3 way: `docker buildx build --platform <script's platform> -t <registry>/<services.analyzer.repository>:<services.analyzer.version> --push services/analyzer` (the tag the chart already pins — no version edit) + `kubectl rollout restart`; the UI is seen through the user's `npm run dev`, no UI image. Charts: `helm upgrade --install telark charts/telark -n telark --reset-then-reuse-values --set app.persistence.storageClass=efs-sc …` (`values.dev.yaml` is not a Helm values file). No `services.*.version` / `Chart.yaml` edit, no registry publish beyond the pinned dev tag, no git tag. Seeded incidents live in a dedicated namespace `ai-lab` with app names unique cluster-wide (`lab-pull`, `lab-crash`, `lab-oom`, `lab-multi`), deleted at the end; `shop-prod` / `shop-dev` fixtures are not touched.
- **D12 — Timing instrumentation ships with the feature.** One structured log line per run (`runId`, `gather`, `rules`, `narrate`, `total` seconds, `narrated` bool, failure class; no namespace/app/workload names — the service never logs customer names) so V3 and future support read latency without a profiler.

## Edge cases

| Case | Behaviour | Covered by |
|---|---|---|
| Fast run, model missing / runtime unreachable / pulling | Gather + rules run, document written, cards announced, `lastRun done` with steps 0; `ensure_model` still triggers the auto-pull (connected) so the next run narrates. Never `failed`. Reachable from the UI: in fast mode the analyze route skips its `ready` gate (`api_server.py:176-178`), the UI enables Analyze when `runtime.mode === 'fast'` (`ApplicationInsightsSection.tsx:108`), and the worker no longer idles while a pull runs (`main.py:300`, deep mode only). | S5, S6, S8 |
| Narration timeout, 503 busy (one retry after `BUSY_SLEEP_S` as today), any other Ollama error (`OllamaError` base: 500 model-load / memory refusal, 400), undecodable body, decode error, wrong item count, empty title/summary | Templates stay for the affected items; steps 0 (nothing applied) or 1; run done; timing line says `narrated=false` with the exception class. The narration catches `(OllamaError, ValueError)` — `analyzer._FAILURE_TYPES` omits the `OllamaError` base, which would otherwise escape to `execute()` and stamp `failed/internal` after the cards were written. | S5 |
| Kubernetes API unavailable / tool timeout / k8s_error during gather | Rules run on overview + history only; `run.truncated` true (existing tool contract) → confidence clamped low, no resolves; health degraded with no matching rule → `other` low. | S4, S5 |
| App with no workloads | No candidates, no narration call, empty run done; `resolve_observed` untouched (nothing cached). | S4, S5 |
| Several rules match one workload | One card per subject (existing id rule): precedence oom > image_pull > crashloop > scheduling > probe_failure > resource_pressure > rollout_stuck > config_change_regression > other; evidence refs of every matched rule merged (≤ 4). | S4 |

## Out of scope

Providers, API keys, BYOK, cloud endpoints (never); chatbot / RAG / multi-agent; a UI switch for the mode (D5); FQDN NetworkPolicies (D6); persisted-document changes (D7); Ollama bump (D3); metrics tool; any new dependency in `requirements.txt`; renaming the service.

## Risks

- **Rule coverage vs reality:** events wording differs across Kubernetes versions/runtimes (containerd `BackOff` text, `Unhealthy` messages). Bounded by `other` + low confidence and by V4 on a real 1.3x cluster; match strings are constants so a fix is one line.
- **350M prose quality:** titles/summaries may be flat or echo the facts. Accepted for the default tier (facts are correct by construction); `qwen3:1.7b` documented for better prose; V4 rubric catches invented names.
- **Prompt processing on a contended node:** the node runs the whole product; p95 targets may slip when discovery is busy. V3 records node CPU alongside; targets are for the idle-ish dev cluster.
- **No memory limit on Ollama:** a runaway (e.g. an operator pulling a 7B model on 8 GiB) can pressure the node; the request and the README sizing table are the guard; Guaranteed profile documented.
- **Two writes per run:** a crash between them leaves cards with template prose and `lastRun running`. The XAUTOCLAIM re-delivery does not re-run it while the inflight key (same run id, TTL 540 s) survives — `execute` drops it as `run_in_progress` and `drop_pending` stamps the running lastRun failed (pre-existing behaviour, same as a crash mid deep run); the UI's running deadline covers the gap. The rule cards themselves are kept; no data loss.
- **Old UI / new backend and vice-versa:** additive fields only; the run line shows "0 steps" on old bundles.
- **Ollama 0.17.7 `format` with `minItems`:** grammar support for `minItems` is assumed (JSON-schema → GBNF supports it); S5 tests assert the payload, V3 proves the model returns exactly n items; if not, the fallback (wrong count → templates) already protects the run and D8 drops `minItems`.
- **`memory.max = max` fallback:** the research reads Ollama's source for the `/proc/meminfo` fallback; V1/V2 prove it live before anything depends on it.
