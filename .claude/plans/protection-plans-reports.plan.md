## Approach

PART A extracts exactly four primitives a second on-volume store needs into services/exporter/internal/utils/artifact: WriteAtomic(path, write func(io.Writer) error) (Stage, error) returning the RAW cause plus the stage it failed at, IsWithinBase, IsSafeSegment, and TickAllowed(ctx, rdb, key, ttl) (the Redis-gated GC tick). The snapshot originals (paths.go, persist.go, gc.go gcTickAllowed) become one-line delegates with identical names, signatures, returned errors and log lines, so request.go/storage.go/file.go/def.go and the five staged snapshot test files are untouched and ARE the behaviour pin. The Part A gate (A3) checks the perimeter as a worktree-vs-index diff (the index holds the user's staged environments-tags work and is never asserted empty), test/lint parity against the baseline A0 records, and writes the Part A diff-stat into the workflow journal; V4(a) re-checks that stat (or, if the user committed Part A meanwhile, an empty diff against HEAD) — no scratchpad manifest. PART B: discovery owns the data and rendering; the exporter is a validated byte store on a SECOND PVC (<fullname>-exporter-reports-pvc, REPORTS_PATH=/reports, own route tree reports/plans/*), rendered from the SAME pvc.yaml template as the snapshots claim (one claims list, snapshots document proven byte-identical), mirrored in the release-manager deployment chart. One atomic file per report (/reports/plans/<planID>/reports/<reportID>.json = {meta, files{html,md,json,csv}}, meta FIRST so List streams only the meta prefix); ONE ledger file per plan (/reports/plans/<planID>/ledger.json, Run stored inside; a run mismatch starts empty); a replayed report id answers 200 with the stored meta; exporters/reports.StartReportsGC is its OWN goroutine (own lock key, recover, same SNAPSHOT_GC_INTERVAL_SEC — documented coupling) that removes report directories of plans whose CR no longer exists and stale temp files. The Events-TTL landmine is closed structurally: a leader-gated checkpoint loop (PROTECTION_PLAN_REPORT_CHECKPOINT_SEC, default 900 s, clamped to [60, 1800] s — always below the 1 h Event TTL) merges live PolicyViolation Events into the ledger through its OWN rate-limited dynamic client (per-concern budget, rollback precedent); the merge is time-fenced to [StartedAt, TerminatedAt] and deduplicated by Event UID; EVERY report generation first merges live Events IN MEMORY (so a report is never less complete than the ledger plus what the cluster still holds), and only the leader loop and the boundary capture PERSIST the merged ledger, each under a single Redis NX Acquire (uuid value, busy → skip the write, never skip the merge). Manual Generate is read-only and works after the plan ended: within the retention window it merges live Events for ledger.RenderedPolicies (rows ≤ TerminatedAt) — the recovery path when a boundary capture failed. The boundary capture runs AFTER the terminal patch in svc.Terminate and svc.Cancel — never between cleanup and the patch, because health.repairIfDrifted (not leader-gated, reachable from the status route on any replica) redeploys policies onto any plan that still reads active — and it is ASYNCHRONOUS: reports.Generator.CaptureAsync copies the in-memory plan (which still holds RenderedPolicies/Health), stamps TerminatedAt/By/Phase from the trigger, and runs Generate in a goroutine under a detached 10 s timeout, a recover, and a single capture slot (captures serialize; they never compete with manual renders for the 2-slot manual semaphore). Terminate/Cancel latency and the controller pass are unchanged; no ctx guard is added (recorded as a separate follow-up). Generate and Checkpoint run inside a recover so a panic in gather/render is an error, never a crash-loop of the sequential controller. Report traffic never enters the exporter circuit breaker (direct rest client calls; no ExecuteExporter, no state gate); the checkpoint loop stops at the first exporter failure. Report size is self-bounding (RenderWithinBudget fits the request under 16 MiB by dropping oldest rows, truncated flag); the ledger is bounded by PROTECTION_PLAN_REPORT_MAX_VIOLATIONS × 512-rune messages. Manual renders are bounded by a 2-slot semaphore: overflow → 429 + Retry-After (not 503: the dashboard's own health breaker counts every ≥ 500 from discovery and would blank the UI after five busy answers). Wire format: the ledger crosses the exporter boundary as pre-marshalled JSON (rest shared.Client.CreateJSON(endpoint, json.RawMessage) — never through the reflection mapper) and every DTO carries explicit camelCase json tags, pinned by round-trip tests against the real mapper and the real client. Four stdlib formats (HTML with print stylesheet = the PDF path, Markdown, JSON, CSV), zero new Go dependencies, no CRD change, no data-module change, no new deny actions, no Redux, no job table, no user-name lookups. Exactly four settings: app.persistence.reportsSize, REPORTS_PATH, PROTECTION_PLAN_REPORT_MAX_VIOLATIONS, PROTECTION_PLAN_REPORT_CHECKPOINT_SEC; every other knob is a constant. The UI downloads via Client<Blob>(exporterApiClient, ..., {responseType:'blob'}) with the session token in the X-Session-Token header only, and the Reports card is always rendered (sibling hooks are ungated; the exporter's Read requirement is the guard). Order: Part A (A0 baseline+precondition → A1 → A2 → A3 gate) → rest DTOs → chart PVC (both charts) → exporter store → exporter routes → rest client → discovery client → domain → boundary hook → checkpoint loop → handler → UI → docs → verification.

## Decisions (defaults the user can override)

### Where is the generic seam and what shape does it take?
**Choice**: One new package services/exporter/internal/utils/artifact (artifact.go + types.go): WriteAtomic(path string, write func(io.Writer) error) (Stage, error) where Stage ∈ {StageNone, StageTempCreate, StageTempWrite, StageTempClose, StageRename} and the returned error is the RAW cause (never wrapped); IsWithinBase(target, base string) bool; IsSafeSegment(id string) bool; TickAllowed(ctx context.Context, rdb *redis.Client, key string, ttl time.Duration) bool (the Redis-gated periodic-sweep gate lifted verbatim from exporters/snapshot/gc.go gcTickAllowed, keyed by name). Temp naming uses constants.SnapshotTempSuffix internally. Root path is always an explicit parameter; no Store type, no registry, no interface.

**Why**: Caller census (verified): outside utils/snapshot only def.go:40 WriteSnapshotJSON, :151 FormattedFileSize, :213/:539 IsWithinBase are called; inside, request.go:109/:158, storage.go:214/:217, file.go:21 call unqualified; gcTickAllowed is called once (gc.go:34). Delegating wrappers with the same names keep every one of those files at zero diff. Returning (stage, raw err) keeps the four ErrSnapshot*Context log lines and the error passed to LogAndSendResponse byte-identical. TickAllowed is lifted (revision 4) so the reports sweep does not copy a 12-line lock gate, per C3.

### What does the C3 'scope identifier' map to? (explicit question for the user — default recorded)
**Choice**: A scope is a NAMED SET of five things, not a type: {root env + default (SNAPSHOTS_PATH → /snapshots | REPORTS_PATH → /reports), PVC helper (telark.exporterSnapshotsPvcName | telark.exporterReportsPvcName) + size key (app.persistence.size | reportsSize), mount path (= root), route prefix (snapshots/* | reports/plans/*), GC lock key (exporter:snapshot:gc | exporter:reports:gc)}. Both scopes run over the shared mechanism = package artifact (WriteAtomic, IsWithinBase, IsSafeSegment, TickAllowed) + the single pvc.yaml claims template. NOT shared (deliberately, ~10 lines each): envs/reports.go InitReportsPath/GetReportsPath and main.go initReportsConfig (env parsing in the snapshot shape), and the reports store's own layout functions. The existing envs.ScopeDefinition{Name, Namespaced} registry stays what it is: the snapshot sub-tree list under ONE root; it cannot express a second root (C2), so it is not reused. USER OVERRIDE: if you want a `Store{Root, Perm, LockKey}` value both scopes instantiate, say so; the plan then adds it to package artifact in A1 and both envs files construct one.

**Why**: Revision-3 review: the plan answered 'nothing named scope' to a user-fixed constraint. This records the mapping explicitly and puts the one remaining design choice (a tiny Store value vs two 10-line env files) to the user instead of deciding it silently.

### Who renders the document?
**Choice**: Discovery gathers and renders all four formats in memory (core/plans/protection/reports); the exporter stores and serves bytes.

**Why**: Discovery owns the plan lifecycle and the Events read path; the exporter cannot import rest clients and must not learn plan semantics.

### How does the report cover more than the last hour of Events (the retention landmine)?
**Choice**: A leader-gated checkpoint loop (controllers/plans/protection/checkpoint.go; interval from PROTECTION_PLAN_REPORT_CHECKPOINT_SEC, default 900 s, clamped to [ReportCheckpointMinSec = 60, ReportCheckpointMaxSec = 1800] with a log line when clamped; one catch-up run on leadership start) merges live Events into ONE ledger per plan stored by the exporter at /reports/plans/<planID>/ledger.json (Run stored inside; when Run != RunKey(plan) the ledger starts empty and is overwritten — the previous run is already preserved in its final report). Merge = time fence [plan.StartedAt, plan.TerminatedAt-if-set] on Timestamp, dedup by Event UID (new EventUID field on ProtectionPlanViolation), CapMessage at 512 runes, then violations.Page(rows, max) newest-first with truncated = total > max. The ledger also stores RenderedPolicies (set on each persisted merge) and one LedgerCheckpoint{At, Health, ViolationsSeen} per merge that ran Collect. Event LISTs use the Generator's OWN dynamic client (kcorek8s.NewDynamicClientWithRateLimit with the rollback budget constants) so the checkpoint burst on leadership acquisition never starves CleanupByPlanID/Deploy on the applier's client; each plan's Checkpoint runs under context.WithTimeout(ctx, DefaultReportCaptureTimeout); the loop breaks at the first exporter failure. EVERY Generate (boundary and manual) = load ledger → Merge live IN MEMORY → render from the merged ledger; only the leader loop and the boundary capture PERSIST (single Redis NX Acquire, key lock:reports:ledger:<planID>, value uuid.NewString(), TTL DefaultLockTTL; busy → LogLedgerLocked and skip the write only). Post-end: when TerminatedAt is set and now − TerminatedAt < violations.RetentionWindowDuration, Merge uses ledger.RenderedPolicies (plan.RenderedPolicies is blank after the terminal patch) and keeps rows ≤ TerminatedAt — so a manual report generated within the hour after a FAILED boundary capture is still complete. Coverage lists checkpoint count, first/last checkpoint, every gap longer than the retention window, and the trailing gap.

**Why**: Boundary-only capture covers the last hour. Revision-3 review: (1) the lock-busy branch and the TerminatedAt early-return threw away recoverable data; merging in memory is free because the live rows are already read; (2) name-only filtering attributed the previous run's Events to a reactivated run — the time fence closes it; (3) three writers needed a wait loop; with manual Generate read-only there are two writers (leader loop on the leader, boundary capture on whichever replica handled Cancel), one Acquire + uuid (rollback precedent) is enough and a lost update costs at most seconds of Events in the post-end ledger while the final report itself is complete; (4) per-run ledger files were dead data after Reactivate. USER DECISION (default = PVC ledger): a Redis hash keyed by EventUID (HSET ledger:<plan> <uid> <row> + a meta key, capped by HLEN) would remove the two ledger routes, two rest methods, two wrappers, the lock and the read-modify-write — but Redis is not today the system of record for durable data; say 'redis ledger' to switch. USER OVERRIDE 2: drop B9 and the ledger halves of B5/B7/B8 to accept a one-hour ceiling.

### When is a report generated, and where in Terminate/Cancel?
**Choice**: Both: automatically in svc.Terminate and svc.Cancel AFTER the terminal patch succeeds (active + started plans only), and on demand via POST plans/protection/{id}/reports/generate for any plan that is not draft/scheduled AND has StartedAt set. Order in both methods: CleanupByPlanID(ctx) (as today) → PatchRawOrError terminal patch (as today; on error return as today) → s.reports.CaptureAsync(plan, now, actor, reason, trigger) → (Cancel) the final Get. NO ctx.Err() guard is added anywhere.

**Why**: CRITICAL from the revision-3 review: health/repair.go:29-43 redeploys missing policies whenever the plan still reads active at the source, is NOT leader-gated and is reachable from the status route on any replica; a capture placed between cleanup and the patch stretched that window from milliseconds to 10 s and orphaned Enforce policies after endAt/cancel. Nothing the capture needs requires the CR to read active: it renders from the in-memory copy (RenderedPolicies, Health, TimeRange) and from Events, which outlive Policies. Running it asynchronously after the patch also removes the N × 10 s stall of later activations in the same sequential controller pass and the Cancel latency growth (the UI cancel timeout change is gone). The ctx guard was a changed teardown behaviour riding inside a reports feature (it aborted after a SUCCESSFUL cleanup when the deadline passed) — cut, and listed as a separate follow-up with its own reproducing test.

### Sync or async, how is the boundary capture bounded, and what does the UI show on failure?
**Choice**: Asynchronous and hard-bounded in one place: reports.Generator.CaptureAsync(plan *plans.ProtectionPlan, endedAt, actor, reason, trigger string) <-chan struct{} copies *plan by value, sets TerminatedAt=&endedAt, TerminatedBy=&actor, Phase (TriggerEnd → PhaseTerminated with ReasonExpired; TriggerCancel → PhaseCanceled with the user reason), returns immediately, and in a goroutine: acquire the single capture slot (g.captureSlot chan struct{} of size 1, blocking — captures serialize, never time out waiting), cctx := context.WithTimeout(context.Background(), constants.DefaultReportCaptureTimeout = 10 s) (DETACHED from the caller ctx), Generate(cctx, &copy, actor, trigger), log LogReportCaptured/LogReportCaptureFailed, release, close(done). Generate itself runs under a recover (a panic becomes ErrReportPanic). The rest ReportClient's http.Client timeout equals the capture bound and violations.Collect takes cctx, so nothing inside the capture outlives it by more than one HTTP timeout. Manual generate runs on the handler's detached 30 s ProtectionPlanLifecycleTimeout context. Failure = nothing stored (single atomic file) + message.error in the UI; no pending row ever exists. The returned done channel exists for tests; svc ignores it.

**Why**: The capture must not delay the terminal patch (see above) and must not block the sequential controller; a bounded goroutine after the patch is the smallest shape that does both. A capture slot instead of the manual semaphore: two Generate clicks could otherwise hold both slots for 10 s and starve the one report that cannot be regenerated with full data (captures are already serial — one Terminate at a time, one Cancel per request). The recover closes the crash-loop the review found (pointer fields on never-started/canceled plans).

### Can report traffic affect the exporter circuit breaker?
**Choice**: No, because it never enters it. clients.ReportClient calls the rest reports client DIRECTLY (no circuitbreaker.ExecuteExporter, no NotCounted) and maps the response with the pure ClassifyReportResponse. No read-only state gate either (breakerClosed and its test are cut): during an exporter outage a report call costs at most one 10 s HTTP timeout, the boundary is already bounded by CaptureAsync, and CheckpointReports breaks at the first exporter failure so an outage never costs N × 10 s.

**Why**: In half-open state the breaker allows exactly one probe (CircuitBreakerHalfOpenMaxProbes = 1); any wrapped report call would take it and a report 200 would close the breaker. Not wrapping is the only isolation; the state gate was the most complex part of B6 for the price of one timeout.

### Storage layout, atomicity, read cost and orphan cleanup on the reports PVC?
**Choice**: One JSON file per report written by artifact.WriteAtomic: /reports/plans/<planID>/reports/<reportID>.json = {"meta": …, "files": {html,md,json,csv}} with meta FIRST; ONE ledger at /reports/plans/<planID>/ledger.json. List = ReadDir + ReadMeta(io.Reader) which token-streams to the meta value and STOPS. Download reads one file and serves one field with Content-Type, X-Content-Type-Options: nosniff and Content-Security-Policy: sandbox (no Content-Disposition, no ServeContent — the UI builds the filename and CORS exposes no headers). GC: the exporter's DeletePlanByID removes /reports/plans/<planID> after the CR delete succeeds AND exporters/reports.StartReportsGC — its OWN goroutine started from main.go, ticking at envmanager.GetSnapshotGCInterval() (no new env; SNAPSHOT_GC_INTERVAL_SEC <= 0 disables BOTH sweeps — documented), gated by artifact.TickAllowed(ctx, rdb, constants.ReportsGCLockKey, interval/SnapshotGCLockTTLDivisor), body wrapped in a recover — runs RunReportsGC: lists ProtectionPlan CRs (live = CR names; never sweeps on a failed or empty list) and calls reportsutil.SweepOrphans(root, live, ReportsSweepMinAge = 1 h) which removes every /reports/plans/<id> not in live whose mtime is older than the age gate AND every *.tmp older than the age gate under live plan directories.

**Why**: A single rename makes the whole report appear or not at all. Guideline §6 'Ship the GC with the write path'. Revision-3 review: wiring the sweep into StartSnapshotGC's tick put a Part B edit into the recovery-path GC file, lengthened its tick with EFS RemoveAll, and let a reports panic kill the snapshot GC goroutine; an own goroutine with the shared TickAllowed gate keeps exporters/snapshot/gc.go untouched in Part B. Crashed writes inside a live plan directory left *.tmp files forever; the sweep now removes them past the age gate.

### Report identity and replay semantics?
**Choice**: reportID = <runKey>-<trigger>[-<stamp>], runKey = plan.StartedAt parsed with globalshared.DefaultTimeFormat and formatted 20060102T150405Z (StartedAt nil is rejected before Generate: ManualAllowed and CaptureAsync both require it; an unparsable value is an error); trigger ∈ {end,cancel,manual}, stamp = generation time compact for manual only. The exporter answers a replayed id with 200 and the stored meta, never overwriting.

**Why**: Reactivate reuses deterministic policy names and nulls terminatedAt/By, so planID alone is ambiguous; an abandoned late write after a capture timeout is harmless. The CreatedAt fallback is gone: never-started plans have nothing to report and produced a nil-pointer path in gather.

### How is report size bounded for every preset?
**Choice**: Self-bounding at render time: reports.RenderWithinBudget(doc, constants.ReportRequestBudgetBytes = 16 MiB) renders, measures len(json.Marshal(CreatePlanReportRequest)), and if over budget keeps the newest len(rows)*budget/size*9/10 rows, sets Coverage.Truncated and Coverage.RowsOmitted, and re-renders (at most reports.RenderFitAttempts = 4, else error). The ledger is bounded separately: PROTECTION_PLAN_REPORT_MAX_VIOLATIONS (default 5000, minimal 2000, NO performance override) rows × MaxMessageRunes 512 is proven < 32 MiB by a test with worst-case messages.

**Why**: A fixed row count cannot be proven under the body limit (every row is emitted four times and encoding/json escapes <, > and &). Fitting to the budget makes the bound independent of presets.

### Retention of reports?
**Choice**: Keep the newest constants.ReportsMaxPerPlan = 10 manual reports per plan by meta.generatedAt (constant, no env); boundary reports (end/cancel, at most one per run) are never pruned.

**Why**: Lexical pruning by id would drop a boundary report before older manual ones. Nobody asked for the limit to be tunable.

### Formats and PDF?
**Choice**: HTML (self-contained, inline CSS, @media print stylesheet; the browser's Print command is the PDF path and the UI shows PRINT_HINT), Markdown, JSON (the ReportDocument), CSV (admission-decision rows). No native PDF. Escaping: html/template for HTML; Markdown cells go through html.EscapeString AND pipe/newline escaping; CSV cells whose first rune is one of = + - @ \t \r are prefixed with a single quote; encoding/csv quotes. Content-Type per format lives in EXPORTER constants (constants.ReportContentTypes), not in rest.

**Why**: Both runtime images are FROM scratch with CGO off and no fonts; every PDF path is a new dependency. Event messages are cluster-controlled free text. ContentTypes is used by one handler, so it is not shared API.

### Who may generate, list and download, and what about user identities in the document?
**Choice**: Generate: authz.Write(roledata.ScopeProtectionPlans) on discovery — identical to Cancel. List/download: authz.Read(roledata.ScopeProtectionPlans) on the exporter — identical to the discovery violations route. Create + ledger put/get: authz.Internal. Identities: the document carries RAW user ids and NO display names; the UI list row resolves generatedBy through its users store. Recorded follow-up: reports must adopt the same Denyable action as the violations route the day the 'view violations' deny is wired (today that deny is unwired on discovery too, so reports do not widen a live gap, only a latent one).

**Why**: Resolving names needs Read(ScopeUsers) while download needs only Read(ScopeProtectionPlans). USER OVERRIDE: add a name lookup later and raise the download requirement to Read(ScopeUsers) as well.

### Is a CRD field needed?
**Choice**: No. The report list is the PVC directory; the plan CR is untouched.

**Why**: Avoids the strict-structural-schema prune landmine, a telark-crds release and docs/CRDS.md changes.

### How is the boundary hook made testable when Service holds a concrete exporter client?
**Choice**: It is not made testable through Service. Service.exporter stays *clients.ProtectionPlanClient; no PlanStore interface. All logic worth testing lives in package reports: CaptureAsync (bounded, recovered, serialized, returns a done channel), ManualAllowed(plan) (phase + StartedAt gate), Merge/Checkpoint/Generate (fake ReportStore, fake dynamic client, miniredis). Terminate/Cancel/GenerateReport each gain a few lines whose ORDER is checked by V4(b), not by a unit test.

**Why**: Turning four staged user files into interfaces existed only so a boundary test could build a Service with fakes. With the capture after the patch and asynchronous, the order carries no safety weight beyond 'after the patch', which V4 reads.

### Concurrency bound on rendering, and what status when busy?
**Choice**: Generator holds a buffered channel of reports.MaxConcurrentRenders = 2 for MANUAL renders only (non-blocking try: full → reports.ErrRenderBusy, which the handler answers as 429 Too Many Requests with Retry-After: reports.RenderBusyRetryAfterSec (5)), plus the separate single capture slot for boundary captures. The UI branches on status === 429 alone (no header read) and disables Generate while a request is in flight.

**Why**: Guideline §6 asks for a semaphore with 503 + Retry-After; 503 is deliberately NOT used here because dashboard-ui's health-interceptor counts every discovery status >= 500 towards FAILURE_THRESHOLD = 5 and then suppresses EVERY discovery request — five busy answers would blank the UI. 429 is outside that range, semantically exact, and readable cross-origin in dev (Retry-After is not: x-ware CORS exposes no headers). Recorded deviation from §6 with a user override. Exporter-failure 503s from Generate still count, like every other proxied discovery route today (pre-existing).

### Exporter 4xx surfacing as 503 through discovery?
**Choice**: ClassifyReportResponse maps exporter 400/413 to validation errors (400 via StatusForErr); 5xx/transport/nil stay ExporterError (503). No 422 mapping. Nil response → constants.ErrReportNilResponse (its own message, never the application-patch one).

**Why**: StatusForErr maps every ExporterError to 503; a caller mistake must not read as an outage; a misleading log constant was a review finding.

### Blob download in dashboard-ui (no precedent)?
**Choice**: Client<Blob>(exporterApiClient, `${DOWNLOAD(planId).path}?${URLSearchParams({report, format})}`, {method:'GET', responseType:'blob', timeout}) → URL.createObjectURL → temporary <a download=filename> click → revokeObjectURL on a later tick (setTimeout(…, OBJECT_URL_REVOKE_DELAY_MS = 1000)); filename `${plan.name}-${report.id}.${format}` built client-side; a definite 404 shows DOWNLOAD_MISSING and refreshes the list, anything else shows DOWNLOAD_ERROR.

**Why**: Client() forwards the full AxiosRequestConfig; the session token stays in the interceptor header; the URL carries only planId/report/format. Revoking synchronously after click() can cancel the download in Firefox/Safari.

### Second PVC shape in the charts?
**Choice**: charts/telark: pvc.yaml becomes a range over a two-entry claims list (snapshots: telark.exporterSnapshotsPvcName / app.persistence.size default 1Gi; reports: new helper telark.exporterReportsPvcName / app.persistence.reportsSize default 2Gi), same enabled gate, same $sc handling, same derived accessMode; one new key app.persistence.reportsSize (2Gi; minimal 512Mi; performance 10Gi) in values.schema.json; values-driven volume + mount + REPORTS_PATH env; discovery env PROTECTION_PLAN_REPORT_MAX_VIOLATIONS (5000; minimal 2000) and PROTECTION_PLAN_REPORT_CHECKPOINT_SEC (900; minimal 1800). release-manager/helm/app: its exporter/base/pvc.yaml ranges the same two claims with that chart's `{{ .Values.app.name }}-exporter-<x>-pvc` naming; app.persistence.reportsSize; the same env/volume/mount entries.

### Which knobs are tunables and which are constants?
