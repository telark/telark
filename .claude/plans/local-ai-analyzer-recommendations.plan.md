## Approach

- **Feature B — messages (incidents).** The rules already decide the kind; they now also decide a *sub-reason* (`reason`, e.g. `image_pull.not_found`, `crashloop.exit_127`) from the pod status, the event message and the spec limits, and hand the card a small `params` map (workload, pod, container, image, exit code, ready/desired, probe, port, …). The server renders **title** ("web is down: image not found") and **summary** (impact sentence + one factual detail sentence + the existing change-correlation sentence) from per-reason templates in `constants.py`; the UI renders **Why** (cause) and **What to do** (≤ 4 kubectl-free steps) from per-reason constants, and a collapsed **Details** block (params, evidence refs, raw event message, first/last seen, runs). The templates alone make a rules-only card complete; narration stays an optional polish of title/summary with a stricter fact check (numbers, sub-reason phrase, other-kind vocabulary) and never runs for recommendations.
- **Feature A — recommendations.** A new pure `recommendations.py` evaluates 60 deterministic v1 rules (reliability, resources, scaling, security, images, config, networking, change risk, protection, multi-namespace consistency) over inputs gathered read-only by `review.py`: the workload objects and their pods (effective, admission-mutated resources), four namespace lists (Services, PodDisruptionBudgets, HorizontalPodAutoscalers, NetworkPolicies — new get/list RBAC), the Application JSON (metrics, rollbacks, history), rolling usage samples kept by the analyzer, and the protection plans + plan environments read from the exporter with the service token. A rule fires only on complete inputs; a failed or truncated read skips its rule family (no card, no resolve). Recommendations live in the **same insight document** as `category: recommendation` cards (`kind` = rule family, `reason` = rule id), one card per (workload, rule), with their own lifecycle: refreshed per review, `updated` only when their facts change, resolved when a complete review no longer finds them, dismissible. Every analysis run reviews its app right after its final write; an in-process sweep reviews apps whose generation changed first, then every app at most once per `ANALYZER_REVIEW_INTERVAL_SEC`, rate-limited and yielding to queued analysis jobs.
- **Feature C — cluster-wide Insights page.** Discovery (the existing read owner of insight documents, x-ware authz, horizontally scaled, readable while the analyzer is off) gains `GET /api/v1/insights/get`: paginated, filtered, sorted and counted from a per-replica in-memory row index. The analyzer service maintains a Redis sorted set `analyzer:index` (member `ns/name`, score = last write ms) on every document write/delete; discovery refreshes its index incrementally (range by score since the last refresh, `MGET` in batches) every 15 s and resyncs membership every 5 min, so a request never touches Redis (no N+1). The UI adds an `Insights` sidebar entry and page (filters: category, kind, severity, state incl. derived `stale`, triage, namespace, environment, search; sort by severity/recency; counts; pagination; rows link to the app's insights section), polling with ETag/304. Triage (acknowledge, dismiss, reopen) is a new analyzer route that writes the card (single writer). No new permission key: Read(applications) views, Contributor on applications triages — the same requirements as the per-app read route and Analyze.

## Decisions (defaults, recorded and applied — no confirmation round was requested)

- **D1 — Scope and order.** One plan, three features, one rollout: contracts (internal/data, internal/rest) → analyzer (B, then A) → discovery (C) → chart → UI → docs → live verification → adversarial review. No CRD change, no GlobalConfig field, no exporter code change.
- **D2 — Who renders which text (Feature B).** Server (Python templates) renders title + summary — the facts, the only fields narration may rephrase, and what older UIs, the Insights page rows and any future notifier read. The UI renders cause (Why), next steps (What to do) and Details from `reason` + `params` using i18n-ready constants (`INSIGHT_GUIDANCE`), with a per-kind fallback for an unknown reason and today's rendering for documents without `reason`. Params carry every value the texts need, so a later i18n pass can render title/summary client-side without a contract change.
- **D3 — Message structure and limits.** Title `{workload} {state}: {what}` (state: `is down` when 0 ready, `is degraded` when some ready, omitted when status unknown or all ready — then `{workload}: {what}`); target ≤ 80 chars for names ≤ 30 chars, hard cap 120 (Go). Summary `{impact} {detail}{change}`: impact `0 of N replicas are ready, so {workload} is not serving.` / `R of N replicas are ready.` / omitted; detail = one factual sentence per reason; change = the existing correlation sentence; target ≤ 240 without the change sentence, hard cap 400. UI cause ≤ 220 chars, ≤ 4 steps of ≤ 140 chars. Params ≤ 16 keys (the largest set, `crashloop.probe_kill`, needs 13), each value ≤ 120 chars; secret values are never stored (names only); for exec-probe failures (`failure: command`) the raw message is not stored in params (it is the command's own output).
- **D4 — Contract (persisted document).** `Insight` + `category` (`incident`\|`recommendation`, omitempty; empty = incident), `reason`, `params map[string]string`, `triage {state, by, at}` (all omitempty); `AppInsights` + `lastReviewAt` (omitempty). New constants for categories, the 10 recommendation kinds, evidence types `spec`/`object`/`metric`/`plan`, triage states/actions, caps. Discovery decodes the document into the Go struct and re-encodes it (`cache.go:34`), so without a data release + discovery pin bump every new field is silently dropped: this is the one release-gating contract change.
- **D5 — Where recommendations are stored.** Same document, `category: recommendation`. One writer (analyzer, in-process lock), one TTL, one read path (per-app route + index), SSE event names reused. The incident functions (`merge`, `resolve_observed`, `resolve_all`, `narrate`, `validate`) are scoped to `category != recommendation`; recommendations get their own merge/resolve. A separate key would need a second discovery read path and a second index for no gain.
- **D6 — Recommendation identity.** `kind` = rule family (`reliability`, `resources`, `scaling`, `security`, `images`, `config`, `networking`, `change_risk`, `protection`, `consistency`); `reason` = `<family>.<rule>`; `subject` = `<kind>/<name>` of the workload, `service/<name>`, or `application/<name>` for app-level rules; id = sha256(`ns|app|subject|reason|workloadNamespace`)[:16] — one card per (subject, rule, namespace), container-level findings aggregated into `params.containers`. Exception: the four usage rules (`resources.memory_near_limit`, `resources.cpu_near_limit`, `resources.overprovisioned`, `resources.underprovisioned`) state one container's numbers and a per-resource severity, so their id hashes `subject#<container>/<resource>` — one card per (workload, rule, container, resource). Incident ids are unchanged (`ns|app|subject`), so the two never collide.
- **D7 — Trigger model.** (a) Every analysis run (manual Analyze, incident auto-run) reviews its app — no separate "Review setup" button; the review runs right after the run's final write (so it sees this run's resolves, e.g. for `resources.oom_history`), inside the same inflight lock, with its own write and card events; `analysis.finished` is published before it and is not delayed. (b) An in-process sweep task (every `ANALYZER_REVIEW_TICK_SEC` 120) lists apps (exporter summary view, service token), reviews first the apps whose `history.generation` changed since their last review (this *is* the config-change trigger — no discovery change), then apps whose last review is older than `ANALYZER_REVIEW_INTERVAL_SEC` (7200), at most `ANALYZER_REVIEW_APPS_PER_MIN` (20; minimal 10, performance 60) — ~2 000 apps in 100 min; it yields while `insights:jobs` has entries and takes the per-app inflight lock (skips a busy app). Runs only when `ai.enabled`; `ANALYZER_REVIEW_INTERVAL_SEC=0` disables the sweep (Analyze still reviews). Reviews never call the model and never stamp `lastRun`; they stamp `lastReviewAt` and bump `version` on every write (the UI refetches only on `event.version > version`, useApplicationInsights.ts:115, and discovery drops a document with version 0 and an empty lastRun as legacy, cache.go:39). The in-run review (a) is skipped when `queue_len() > 0` so it never delays queued incident jobs on the single worker; the sweep catches the app up (generation-changed apps first).
- **D8 — Narration.** Unchanged scope for incidents (title/summary only, one call, `granite4:350m` default, 45 s). Recommendations are never narrated (template text is exact; N extra narrations would cost N × 5 s). The fact check gets three more rejections: a number (digit run) absent from the facts, the sub-reason's `what` phrase missing from the narrated title+summary, and a symptom word of another kind (`out of memory`, `oom`, `pull`, `crash`, `evict`, `schedul`, `probe`, `readiness`, `liveness`, `quota`) absent from the template. A rejected item keeps its template (existing behaviour).
- **D9 — Accuracy policy.** Deterministic rules only; every rule declares its input family and fires only when that family's reads were complete (no error, no truncation, no `continue` token); an incomplete family neither creates nor resolves cards. Heuristic rules carry `confidence: medium` and say so in their text. Every v1 rule and every incident sub-reason has three fixtures — positive, negative, false-positive guard — enforced by a registry test that fails when a rule id has no fixture triple. "v1" = decidable read-only and seedable live on telark-dev (time windows are chart values the verification lowers); everything else is catalogued as later with its unlock.
- **D10 — Usage-based rules.** No metrics-server or cAdvisor access. The review appends the Application's `metrics.workloads[].usage` (per container, max over instances) to an analyzer-owned rolling sample list (Redis hash `analyzer:usage`, field `ns/name`, ≤ 48 samples, deduplicated on the usage timestamp, GC'd with the app). Rules need ≥ `ANALYZER_USAGE_MIN_SAMPLES` (12) samples spanning ≥ `ANALYZER_USAGE_MIN_SPAN_SEC` (43 200) and use the p95; over-provisioning only above absolute floors (CPU request ≥ 100m, memory request ≥ 128Mi); suggestions are rounded (10m / 16Mi) and never below the floor usage × 1.1.
- **D11 — RBAC.** Analyzer ClusterRole gains get/list on `services`, `policy/poddisruptionbudgets`, `autoscaling/horizontalpodautoscalers`, `networking.k8s.io/networkpolicies`. Never ConfigMap/Secret contents, nodes, metrics, RBAC objects or writes. Existing pods/events/workloads rules unchanged.
- **D12 — Production detection.** An app is production when any of its namespaces matches `ANALYZER_PRODUCTION_PATTERN` (default `(^|[-_.])(prod|production|prd)($|[-_.])`, case-insensitive) or a covering plan's environment category name matches it. Production raises `reliability.single_replica`, `reliability.no_pdb` from info to warning and enables the two protection rules.
- **D13 — Protection-plan inputs.** Analyzer reads `plans/protection/get` and the `plan-environments` categories from the exporter with its service token (Internal identity; both routes accept it), cached for one sweep tick. Covered = a plan in phase `active` or `scheduled` whose scope lists the app (applications scope) or one of its namespaces (namespaces scope), minus exclusions that name every app workload. A failed read skips the protection family.
- **D14 — Recommendation lifecycle.** Found → `open` (new) or unchanged status with `lastSeenAt` refreshed (no `runs` bump, no event); facts changed (params fingerprint) → `updated` + `insight.updated`; not found by a complete review of its family → `resolved` + `insight.resolved`; found again → reopened. Cap 40 per app (most severe first, then reason order); resolved kept 7 days (existing prune). Recovery jobs and `resolve_observed` never touch recommendations.
- **D15 — Triage.** Actions: `acknowledge` (incidents and recommendations), `dismiss` (recommendations only), `reopen` (clears triage). Stored on the card as `triage {state, by: <userID>, at}`; route `POST /api/v1/insights/applications/{namespace}/{name}/insights/{id}/triage` on analyzer (single writer), requirement Contributor on applications (same as Analyze), `userID` taken from the auth-service permissions response analyzer already calls. A dismissed recommendation stays dismissed while its params fingerprint is unchanged; a fingerprint change, a resolve or a reopen clears triage. Acknowledge is cleared when the card resolves. 400 unknown action, 404 unknown id, 409 dismiss on an incident / acknowledge on a resolved card.
- **D16 — Cluster page backend owner.** Discovery: it already serves insight documents (`handlers/insights/handler.go:33-61`, `Read(applications)` at `authz/requirements.go:45`), keeps working while the analyzer is disabled, scales horizontally and already has the plans client (`clients/protectionplans.go:51 List`). Analyzer is single-replica and would couple page availability to the analyzer. Analyzer only adds the `analyzer:index` ZSET write.
- **D17 — Permissions.** No new permission key or deny action: telark grants are scope-level (x-ware `Grants{Levels, Denied}`, no per-app grants), insights are application data, so the page and the list route use `Read(applications)` like the per-app route, and triage uses Contributor on applications like Analyze. Rows are filtered by the GlobalConfig excluded namespaces exactly as the per-app route does. A denyable `triageinsights` action can be added later without a contract break.
- **D18 — Live updates on the page.** ETag polling every 15 s (`If-None-Match` → 304), one poller per tab, paused while the tab is hidden. SSE is not used for the cluster page: subscriptions are per app (`events.py:26-39`, no wildcard) and the list is served from discovery's index, so an event would still need a list refetch. App details keeps its SSE stream.
- **D19 — States and filters.** Stored: `open`, `updated`, `resolved`. Derived server-side: `stale` = active and `lastSeenAt` older than `INSIGHTS_STALE_AFTER_SEC` (86 400, = the UI's `INSIGHTS_STALE_MS`). Triage filter separate (`untriaged`, `acknowledged`, `dismissed`, `all`). Default view: states open+updated+stale, triage ≠ dismissed, sort severity.
- **D20 — Environment filter.** Discovery maps app → environment ids from non-terminal plans (`active`, `scheduled`, `pending_approval`, `draft`) listed via `ProtectionPlanClient.List` once per index refresh cycle (cached 60 s): applications scope → those app names, namespaces scope → apps in those namespaces. An app no plan names has no environment. The UI resolves ids to names with the existing `plan-environments` categories store.
- **D21 — List endpoint.** `GET /api/v1/insights/get` (rest `insightseps.List`): `category`, `kind` (csv), `severity` (csv), `state` (csv), `triage`, `namespace` (csv), `environment`, `q` (case-insensitive substring of app, namespace, subject, title), `sort` (`severity`\|`recent`), `page` (1-based), `pageSize` (1–100, default 25). Response `{items, total, page, pageSize, counts{bySeverity, byCategory, byState}, indexedAt}`; counts are over the filtered set before paging. 400 on an invalid value, 503 + `Retry-After: 5` until the first index load completes, `ETag` = index version + normalized query.
- **D22 — UI placement.** App details: the existing insights section shows incidents only, each card gains Why / What to do / Details and Acknowledge; a new Recommendations section below it groups by family with severity filter, a show-dismissed toggle, Dismiss/Reopen, and the line "Setup reviewed {time} ago" (or "Not reviewed yet"). Sidebar: `Insights` under DISCOVERY after Applications; route `/insights`; rows link to `APP_ROUTES.APPLICATION_DETAILS` = `/applications/<name>/details#insights` (app.ts:25; no namespace in the route) and the section scrolls into view below the sticky header (`scroll-margin-top`). UI texts name sections by their real labels: the Protection Plans page (sidebar, under Discovery — not 'Governance'), the Snapshots section / Manage snapshots (not 'History') for rollbacks, History Changes for change entries.
- **D23 — Budgets and targets.** Review: ≤ 1.5 s p95 wall, ≤ 4 namespace lists + 2 reads per workload (cap `ANALYZER_REVIEW_WORKLOADS_MAX` 10), 5 s per read, 20 s review wall. Sweep: 20 apps/min default. List endpoint: p95 ≤ 150 ms server time at 2 000 apps / 30 000 rows; discovery index ≤ 25 MiB at that scale; incremental refresh ≤ 200 ms steady state. Incident cards still visible ≤ 2 s after Analyze (the review never delays the first write).
- **D24 — Verification builds.** Analyzer dev image via `docker buildx` at the pinned tag (NEXT_SESSION §3.3); discovery via `scripts/local-build-push.sh -n discovery` (not a go.work build: for each of `-r data,kcore,rest,x-ware` (default) whose local checkout under ../internal differs from the version discovery's go.mod pins, it rsyncs the checkout into a temp build context, runs `go mod edit -replace` + `go mod tidy` there, builds the service Dockerfile for the node arch and pushes to the tag `services.discovery.version` already pins — the repo's go.mod, the chart and every version stay untouched; `-n` skips its own restart so the helm upgrade does the single rollout); UI via the user's `npm run dev`. `helm upgrade --install telark charts/telark -n telark --reset-then-reuse-values --set app.persistence.storageClass=efs-sc --set app.ollama.enabled=true` (+ verification-only `--set` overrides that are reverted at the end). Seeds live in new namespaces `ib-lab`, `ib-lab-q`, `recs-lab`, `recs-lab-prod`, deleted at the end with the protection plans created for them; `shop-*` fixtures untouched.

## Feature B — message catalog (52 incident sub-reasons)

### Structure (every incident card)

- **State/impact (server, all incident reasons):** `state` = `is down` (ready 0 < desired), `is degraded` (0 < ready < desired), none otherwise; `impact` = `0 of {desired} replicas are ready, so {workload} is not serving.` / `{ready} of {desired} replicas are ready.` / omitted when the status was not read.
- **Change sentence (server):** unchanged v2 correlation: ` It began {minutes} min after change gen {generation}: {field} {old}→{new}.`; adds params `generation`, `change`.
- **Conditional UI step (all incident reasons):** when `params.generation` is set, the UI appends "This began after change gen {generation}. If the change caused it, roll back to the snapshot taken before it from the application's History."
- **Resolution line (UI, all incident reasons):** "This incident resolves on its own once the workload is healthy again."
- **Details block (UI, all):** params as a label/value table (labels in `INSIGHT_PARAM_LABELS`), evidence refs, `params.message` (raw event text) in monospace, first/last seen, runs, triage by/at.

### Probe failure texts (`params.failure`)

| failure | detection | `failureText` (server) | `failureCause` (UI) |
|---|---|---|---|
| `refused` | message contains `connection refused` | connection refused on port {port} | Nothing listens on the probed port: the application is not started yet, crashed, or listens on another port. |
| `http_status` | message contains `statuscode: NNN` | the endpoint returned HTTP {status} | The application answers, but with an error status on the probed path (a wrong path, or the application reports itself unhealthy). |
| `timeout` | message contains `timeout`, `timed out` or `context deadline exceeded` | no answer within {timeout}s | The application did not answer within timeoutSeconds: it is overloaded, blocked, or the timeout is too short. |
| `command` | exec probe message (`command` … `exit code`/`exited`) | the check command failed | The check command ran inside the container and returned a failure. |
| `other` | no marker | {message} | The probe failed; the message states why. |

## Feature C — cluster-wide Insights page (summary)

- Backend: discovery `GET /api/v1/insights/get` (D16, D21) from a per-replica row index fed by the `analyzer:index` ZSET (delta every 15 s, resync every 5 min, MGET batches of 200); no Redis on the request path; 503 until the first load; ETag/304.
- States: open / updated / resolved stored, `stale` derived; triage filter separate; default view hides resolved and dismissed (D19).
- Filters: category, kind (incident kinds + recommendation families), severity, state, triage, namespace, environment (from plans, D20), search; sort severity/recent; counts before paging; pagination ≤ 100.
- Triage: analyzer route, Contributor on applications; acknowledge / dismiss (recommendations) / reopen (D15).
- UI: sidebar `Insights` (Read applications, no new key — D17), page with toolbar, counts, table, row → app details `#insights`; ETag polling every 15 s while visible (D18).

| case | behaviour | covered by |
|---|---|---|
